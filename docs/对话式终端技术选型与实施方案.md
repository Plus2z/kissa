# 对话式终端 —— 技术选型与实施方案

承接上一份 UI 设计方案,这里聚焦"用什么技术做、怎么落地"。这个产品有一个特殊性必须放在最前面强调:**它本质上是给用户一个可以执行任意 shell 命令的远程 PTY,这是一个安全敏感度极高的产品**,所以技术方案里"隔离与安全"和"功能实现"同等重要,不能只顾体验。

---

## 二、前端实施要点

### 1. 消息流渲染
用**虚拟列表**(react-virtuoso)承载聊天气泡列表,不要用普通 `map` 渲染全部 DOM——终端场景下历史消息量会远超普通聊天软件(一次 `npm install` 可能几百行),不做虚拟滚动会很快卡顿。

### 2. 消息数据模型
建议前端统一用一种消息事件模型,而不是"字符串拼接",方便切换渲染组件:

```typescript
type TerminalMessage =
  | { type: 'command'; id: string; text: string; cwd: string; timestamp: number }
  | { type: 'output_text'; id: string; commandId: string; content: string; stream: 'stdout' | 'stderr' }
  | { type: 'output_stream'; id: string; commandId: string; content: string; status: 'running' | 'done' | 'failed'; progress?: number }
  | { type: 'output_structured'; id: string; commandId: string; kind: 'file_list' | 'table' | 'diff' | 'json'; data: unknown }
  | { type: 'input_request'; id: string; commandId: string; kind: 'password' | 'confirm' | 'text'; prompt: string }
  | { type: 'fullscreen_program'; id: string; commandId: string; program: string; status: 'active' | 'exited'; summary?: string }
  | { type: 'system'; id: string; text: string } // cd、resize、会话事件等
```

每种 `type` 对应一个独立的 React 渲染组件,新增命令类型的特殊渲染时只需要新增一个 case,不影响其他部分。

需要强调的是,这个模型描述的是**增强视图层**的数据,不是系统的渲染主干。主干是"PTY 原始字节流 → 前端常驻的终端仿真状态机(xterm.js)";`TerminalMessage` 是旁路生成的标注,某个增强消息缺失或损坏时,前端用真相层中该命令区间的终端屏幕内容兜底,而不是空白。

### 3. 全屏程序的嵌入方式
`fullscreen_program` 类型的气泡默认折叠展示,用户点击展开时,动态挂载一个 `xterm.js` 实例,并把该会话此后的原始字节流(不经过分类器,原样)直接喂给 xterm。退出全屏态(检测到 `\x1b[?1049l` 或进程退出)时:
- 卸载 xterm 实例
- 请求后端返回一段"摘要"(比如文件是否保存、diff 行数),或前端自己根据退出前后的 `git diff`/文件哈希做简单摘要

### 4. WebSocket 客户端
自己封装一层而不是裸用原生 WebSocket,至少处理:
- 断线自动重连 + 指数退避
- 重连后请求"会话回放"(见后端部分)保证消息不丢
- 心跳(ping/pong)检测连接存活

## 三、后端实施要点

### 1. 会话(Session)= 一个隔离容器 + 一个 PTY 进程

**这是整个系统安全性的核心**。不能让用户的 shell 直接跑在你的应用服务器进程里。推荐架构:

```
用户发起会话
   → 会话管理服务(Fastify)分配一个隔离容器(Docker exec 或新建 Pod)
   → 容器内跑一个受限 shell(非 root、只读挂载敏感目录、资源配额)
   → 容器内起一个轻量 agent(用 node-pty spawn 一个 shell 进程)
   → agent 通过内部 WebSocket/gRPC 把 PTY 字节流转发给会话管理服务
   → 会话管理服务再转发给前端 WebSocket
```

- **资源限制**:cgroups 限制 CPU / 内存 / 进程数(防止 fork 炸弹),`ulimit` 限制文件描述符
- **网络隔离**:默认不给容器外网访问权限,除非产品明确需要(比如允许 `curl`/`npm install`)
- **文件系统隔离**:每个会话独立的可写层(overlay),会话结束/超时自动销毁,避免数据残留和跨会话污染
- **权限**:容器内用非 root 用户运行 shell,禁用危险的 `--privileged`、避免挂载 docker.sock 等

如果目标用户群体是"开发者在自己机器上用",而不是"多租户 SaaS",可以适当简化,比如直接起本地子进程 + node-pty,不做容器隔离——但只要产品要给外部用户用(哪怕是内部同事共享一台服务器),就必须做隔离,这个不能省。

### 2. 命令分类器放在哪一层?扮演什么角色?

**角色定位(先于位置)**:分类器是**增强选择器**,不是渲染管道的必经节点。系统的数据流主干是"PTY 原始字节流 → 前端终端真相层(xterm.js)",这条主干永远完整、不被分类器过滤或改写;分类器在这条主干旁边做旁路分析,输出结构化标注事件(增强视图选择、危险命令标记等)。分类器崩溃、规则超时、输出异常,影响的只是"没有增强",终端交互本身不受影响。

建议放在**会话管理服务**(而不是前端,也不是容器内 agent),原因:
- agent 层只管字节流转发,保持越简单越好,方便审计和替换
- 前端做分类判断的话,恶意/异常数据都要在客户端信任处理,不安全也不利于统一维护规则
- 分类器需要维护"危险命令名单""全屏程序名单""ANSI 特征探测"等规则,这些规则应该能够热更新,放在服务端便于统一升级
- 作为独立旁路模块,它可以随时整体禁用(降级为纯终端模式)而不需要改动主干代码

分类器实现上是一个轻量状态机,对每个会话维护当前状态(`idle` / `running_sync` / `running_stream` / `fullscreen` / `awaiting_input`),根据新到达的字节流特征做状态迁移,并把迁移结果作为**标注事件**推给前端。原始字节流与标注事件走两条逻辑通道:前者是事实,后者是建议。

### 3. 危险命令拦截

前端做"发送前拦截确认"只是 UX 层面。服务端也应该有一层规则(可配置的黑名单/白名单),对识别到的高危命令(如 `rm -rf /`、`:(){ :|:& };:` fork炸弹特征等)做二次确认或直接阻断,不能只信任前端的拦截逻辑,因为前端可绕过。

### 4. 会话持久化与断线重连

- 每条消息事件落库(PostgreSQL,简单的一张 `messages` 表:`session_id, type, payload(jsonb), created_at`)
- 前端断线重连后,带上 `last_message_id`,服务端从数据库/Redis 缓冲区回放该会话在断线期间的消息
- 后端 agent 与容器内 PTY 进程的生命周期与 WebSocket 连接**解耦**——用户断网/关闭浏览器,后台命令(如长时间的 `npm install`)应该继续跑,重连后能看到最新状态,这类似 `tmux`/`screen` 的持久会话思路。实现上可以直接用一个真正的 `tmux` 在容器内包一层,天然获得"断线不丢会话"的能力,减少自己造轮子的成本。

## 四、通信协议设计(WebSocket 消息格式建议)

用统一的 JSON envelope(如果后续要传输大量二进制内容,可以对 `output_stream` 类型使用二进制帧优化性能,MVP 阶段先用 JSON 文本帧即可):

```json
// 客户端 → 服务端
{ "type": "command", "sessionId": "s1", "text": "npm install", "clientMsgId": "c123" }
{ "type": "stdin", "sessionId": "s1", "commandId": "cmd456", "data": "y\n" }
{ "type": "resize", "sessionId": "s1", "cols": 120, "rows": 32 }
{ "type": "signal", "sessionId": "s1", "commandId": "cmd456", "signal": "SIGINT" }

// 服务端 → 客户端
{ "type": "output_stream", "commandId": "cmd456", "content": "...", "status": "running", "progress": 0.4 }
{ "type": "fullscreen_program", "commandId": "cmd456", "program": "vim", "status": "active" }
{ "type": "input_request", "commandId": "cmd456", "kind": "password", "prompt": "[sudo] password for user:" }
```

## 五、部署架构建议

MVP 阶段(验证产品,单机可承载):

```
Nginx(TLS 终结 + WebSocket 反代)
   → Fastify 服务(会话管理 + 分类器 + 消息落库)
      → 本地 Docker(每会话 docker exec 一个隔离容器)
   → PostgreSQL(消息与会话记录)
   → Redis(会话状态缓存、在线状态)
```

规模化阶段(多租户 SaaS):

```
Nginx / API Gateway
   → 会话管理服务(无状态,可水平扩展)
   → Kubernetes(每会话一个短生命周期 Pod,资源配额 + 网络策略隔离)
   → PostgreSQL(主存储)
   → Redis / NATS(跨实例的会话事件路由,因为用户的 WebSocket 连接和实际跑命令的 Pod 可能不在同一台机器)
   → 对象存储(超大输出/日志归档)
```

## 六、实施路线图(建议分阶段)

**阶段一(MVP,2-4周)**
- 单机部署,node-pty 直接 spawn 本地 shell(暂不做容器隔离,先在内部/可信环境验证体验)
- 先把**终端真相层**做扎实:前端常驻 xterm.js 会话状态机,完整消费 PTY 字节流,WebSocket 通信打通——这是后续一切增强的地基和兜底
- 命令气泡 + 纯文本输出气泡(最简单的增强视图)
- 支持基本的 Ctrl+C 中断

**阶段二(核心差异化能力,3-4周)**
- 命令分类器(旁路标注):区分同步命令 / 流式长任务 / 全屏程序 / 等待输入
- 全屏程序的内嵌渲染(直接呈现真相层,含"检测到全屏前的字节重放")
- 密码/确认类交互式输入组件

**阶段三(体验打磨,2-3周)**
- 结构化输出渲染(文件列表、git diff、JSON 树)
- 危险命令前端+后端双重拦截
- 断线重连与消息回放

**阶段四(安全加固与规模化,持续)**
- 引入容器隔离(Docker → 视规模再评估是否上 Firecracker/gVisor)
- 资源配额、网络隔离、审计日志
- 多会话/多标签管理,K8s 编排,水平扩展

## 七、几个容易被低估但很关键的决策点

1. **不要自己写 ANSI/VT100 解析器去做全屏程序渲染**——直接复用 xterm.js,这是业界(包括 VS Code 集成终端、各类云端 IDE)公认的标准方案,自研成本高且坑多。
2. **安全隔离不是后期可以"补"的事**,如果一开始架构上没有把 shell 执行放在隔离沙箱里,后期迁移成本非常高,建议哪怕 MVP 阶段体验上简化,架构上也预留容器化的接口。
3. **优先用 `tmux` 包一层做会话持久化**,而不是自己实现"进程与连接解耦"的状态管理,能省很多工程量。
4. **命令分类器规则要做成可配置、可持续迭代的**,不要写死在代码里——不同命令的输出格式差异很大(不同 Linux 发行版、不同版本的工具输出都可能不同),这部分注定需要长期打磨。
5. **终端真相层是一切的地基**:原始字节流 → 前端终端仿真状态机这条主干必须在第一周就打通并保持纯净(不被增强逻辑污染)。增强视图(卡片、进度条、输入组件)全部以"可拆卸叠加"的方式实现,任何一处失败都能降级为纯终端交互——这决定了产品的鲁棒性下限,也决定了后续每个增强功能的风险上限。

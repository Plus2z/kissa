# 对话式终端(Chat Terminal)设计方案

## 一、设计目标与核心矛盾

**目标**:把终端的输入输出映射成聊天气泡,降低使用门槛、增强可读性、便于回溯历史。

**核心矛盾**:传统终端是"字符流 + 光标 + 就地刷新"的模型(比如 `top`、`vim` 会不断重绘同一块屏幕区域),而聊天气泡是"离散、追加、不可变"的消息模型。如果不区分命令类型,直接把所有输出塞进气泡,会遇到:

- 全屏程序疯狂刷新,气泡里全是乱码或者无限增长的气泡
- 需要交互输入的命令(密码、确认)卡住,用户不知道怎么输
- 长时间任务(npm install)看起来像"卡死"
- 结构化输出(表格、JSON)读起来很累

所以方案的核心思路是:**以真实终端状态为事实来源(source of truth),分类器只负责选择增强视图;任何分类失败都降级为可用的终端交互**,而不是一刀切。

具体含义:

- 系统中始终存在一个"真相层"——基于终端仿真(PTY 字节流 + 终端状态机,xterm.js)的完整、正确的交互能力。用户任何时候都可以退回这个真实终端视图,它不依赖上层增强逻辑,不会因为分类或解析出错而丢失内容。
- 分类器不再决定"输出如何渲染",而是决定"在真相层之上叠加哪种增强视图"(结构化卡片、进度条、友好输入组件等)。增强视图是**可拆卸的**:规则不匹配、解析失败、数据异常时,卸载增强组件、回退到终端仿真视图即可。
- 由此保证系统的鲁棒性下限:最坏情况下产品退化为一个标准的 Web 终端(xterm.js 直连 PTY),依然完全可用;而不是退化成乱码、空白或卡死的气泡。

## 二、整体架构

```
┌─────────────────────────────────────────┐
│  前端 UI 层 (聊天气泡列表 + 底部输入框)      │
│  - 终端真相层:每会话一个终端仿真状态机        │
│    (xterm.js),始终接收完整 PTY 字节流     │
│  - 增强视图层:分类器输出 → 叠加组件          │
│    (卡片/表格/进度条/输入组件),可随时卸载    │
│  - 降级路径:增强失败 → 回退终端仿真视图       │
└───────────────┬─────────────────────────┘
                │ WebSocket (双向流)
┌───────────────┴─────────────────────────┐
│  中间层:会话管理 + 命令分类器(仅做增强标注)   │
│  - PTY 会话管理(每个"对话"= 一个 shell 会话)│
│  - 命令预分析(静态规则 + 输出特征探测)       │
│  - 原始字节流始终透传 + 附带结构化标注事件     │
└───────────────┬─────────────────────────┘
                │
┌───────────────┴─────────────────────────┐
│  后端:真实 PTY(伪终端)进程                 │
│  - node-pty / python-pty 起一个真实 shell   │
└─────────────────────────────────────────┘
```

**关键决策**:
- 后端必须是真正的 PTY,而不是简单 `exec()` 执行命令拿 stdout。因为很多程序(vim/htop/密码输入)依赖 TTY 特性(行缓冲、回显控制、窗口尺寸)。没有真 PTY,这个产品做不下去。
- 终端仿真状态是全系统唯一的"事实来源"。PTY 的原始字节流永远完整地流向真相层;分类器和增强视图只是旁路消费这份字节流,它们的失败与否不影响真相层的正确性。

## 三、消息气泡的基本类型

| 气泡类型 | 用途 | 视觉特征 |
|---|---|---|
| 用户指令气泡 | 用户发出的命令 | 右侧对齐,等宽字体,显示执行时的 cwd |
| 纯文本输出气泡 | 简单命令的 stdout | 左侧,等宽字体,浅色背景 |
| 流式输出气泡 | 长任务的实时输出 | 左侧,带"进行中"动效,可展开/折叠 |
| 结构化数据气泡 | 表格/列表型输出 | 渲染为卡片/表格而非纯文本 |
| 错误气泡 | stderr / 非零退出码 | 红色/警告色调,附带退出码 |
| 交互请求气泡 | 需要用户输入(密码/确认) | 内嵌输入框或快捷按钮,阻塞后续消息 |
| 系统状态气泡 | cd、cwd 变化、会话事件 | 居中、灰色小字,像系统提示 |
| 全屏程序气泡 | vim/top 等 | 显示为"已进入 XX 全屏模式"占位卡片,点击展开为内嵌终端 |

## 四、按命令类型选择增强视图(核心部分)

以下各节描述分类器识别成功时叠加的增强视图。**共同前提**:每一种增强视图都必须有明确的降级路径——识别失败、解析失败或运行中异常时,该气泡回退为终端仿真视图(展示真相层中该命令对应的屏幕内容),内容永不丢失。

### 1. 普通同步命令(`ls`, `pwd`, `cat`, `echo`, `whoami`, `git status` 等)

**特征**:执行快、一次性输出、无需交互。

**处理**:
- 命令气泡 → 直接跟一个输出气泡,退出码非 0 时输出气泡变红并标注 `exit code: N`
- 输出超过一定行数(如 30 行)自动折叠,显示"展开完整输出(共 N 行)"
- `cat` 大文件、二进制文件要做安全截断,并给出"该文件较大,是否查看完整内容"的选项

### 2. 长时间运行 / 流式输出命令(`npm install`, `docker build`, `apt update`, `make`, `pip install`)

**特征**:输出持续追加,过程中经常有进度条(用 `\r` 覆盖同一行)。

**处理**:
- 不要把每次刷新都变成新气泡,而是**同一个气泡内容持续更新(打字机式追加/替换最后一行)**
- 解析 ANSI 的 `\r` 和光标控制符,还原成"进度条"UI 组件(用真实的进度条渲染,而不是保留原始转义字符)
- 气泡右上角常驻一个"停止"按钮(发送 Ctrl+C)
- 命令结束后气泡从"进行中"状态变为"已完成/失败",并可一键折叠只保留摘要(如"npm install 完成,耗时23s,安装187个包")

### 3. 全屏交互式程序(`vim`, `nano`, `top`, `htop`, `less`, `man`, `ssh` 远程会话)

**特征**:接管整个终端屏幕,依赖光标定位重绘,完全不适合拆成气泡。

**处理**:
- 检测到这类命令(维护一个已知程序名单 + 检测"备用屏幕缓冲区"转义序列 `\x1b[?1049h`)时,**不在聊天流里逐行渲染**
- 改为在气泡里插入一张"进入全屏程序"的占位卡片,例如:"📟 已进入 vim (main.py) — 点击展开"
- 点击后弹出一个内嵌的真实终端模拟层(用 xterm.js 这类库),完整还原全屏交互体验
- 退出全屏程序后(检测 `\x1b[?1049l` 或进程结束),自动收起,气泡更新为摘要,例如:"✅ vim 已退出,文件已保存(3行改动)"
- `less`/`man` 这种可以做特化:直接把内容抓取下来渲染成一个"可滚动阅读卡片",而不强制走全屏终端模拟,体验更轻

### 4. 需要用户输入交互的命令(`sudo` 密码、`rm -i` 确认、`npm init` 问答、`ssh` 首次连接指纹确认)

**特征**:程序会阻塞等待 stdin,提示信息可能不换行。

**处理**:
- 检测到 stdout 输出后进程处于等待输入状态(超时未再产生输出 + 光标停留),自动在该气泡下方生成一个**输入区**
- 根据提示文本做语义识别,给出更友好的输入组件:
  - 检测到 "password" 字样 → 渲染密码输入框(遮罩显示,不回显明文)
  - 检测到 `(y/n)` / `[Y/n]` → 渲染"是/否"快捷按钮,点击即发送对应字符+回车
  - 其他情况 → 普通行内输入框,回车即发送
- 用户输入后,该输入区变为已提交状态(密码显示为 `••••••`),避免历史里暴露明文

### 5. 结构化数据输出(`ls -la`, `ps aux`, `git log`, `git diff`, JSON/YAML 输出, `df -h`)

**特征**:输出本身是表格或半结构化文本,原样纯文本展示可读性差。

**处理**:
- 针对高频命令做专门的输出解析器 + 定制渲染组件:
  - `ls -la` → 文件/文件夹卡片列表(带图标、大小、权限、修改时间),支持点击文件名快速 `cd`/预览
  - `ps`/`top` 单次快照 → 可排序表格
  - `git log` → 简化的提交时间线,含 commit hash、message、作者
  - `git diff` → diff 高亮渲染(增删行变色),而不是原始 `+/-` 纯文本
  - JSON 输出 → 可折叠的树形结构,支持复制某个字段
- 无法识别的命令仍走"纯文本输出气泡"兜底,保证不会因为解析失败而丢失内容

### 6. 持续输出 / 后台监控类命令(`tail -f`, `ping`, `watch`, `docker logs -f`)

**特征**:永不主动结束,持续产生新内容。

**处理**:
- 气泡标注"实时流"状态,只保留最近 N 行在气泡内,超出部分可展开查看历史
- 提供醒目的"停止"按钮(发送 Ctrl+C),避免用户找不到怎么打断
- 如果用户在流式命令运行时发送新指令,提示"当前有命令正在运行,是否先停止当前命令"(而不是把新指令的字符误发给正在运行的程序当作输入)

### 7. 危险/破坏性命令的二次确认(`rm -rf`, `git push --force`, `DROP TABLE`, `dd`)

**特征**:命令行本身通常不会二次确认,容易误操作。

**处理**:
- 客户端维护一份危险命令的正则规则库,拦截在**发送前**弹出确认气泡:"⚠️ 该命令会永久删除 /xxx 目录,确认执行?"
- 确认后才真正发给后端 PTY 执行,取消则该指令气泡标记为"已取消,未执行"
- 这一层是纯前端拦截,不依赖命令本身的 `-i` 参数,弥补命令行原生缺乏保护的问题

### 8. 目录切换与会话上下文(`cd`, `export`, `source`, 环境变量变化)

**特征**:不产生"输出",但会改变后续命令的执行上下文。

**处理**:
- `cd` 不生成输出气泡,而是更新界面顶部的"当前路径"面包屑,并插入一条极简的系统提示气泡(灰色小字):"目录切换至 ~/projects/app"
- `export`/`alias` 等同理,用系统提示气泡呈现,避免打断对话流的阅读节奏

### 9. 管道与命令链(`cmd1 | cmd2`, `cmd1 && cmd2`, `cmd1 ; cmd2`)

**处理**:
- 整条命令作为**一个**指令气泡发送(不要拆开各段),因为它们在 shell 层面是一个整体
- 输出气泡如果能识别出链式结构,可在气泡内部用分隔线/小标签标出"cmd1 → cmd2"各阶段结果(尽力而为,优先级不高,兜底方案是整体当作一段输出处理)

### 10. 清屏与历史(`clear`, `history`, `Ctrl+L`)

**处理**:
- `clear` 不清空聊天记录(这是对话式终端和传统终端的本质区别之一),而是折叠/归档当前可见气泡,保留可回溯的历史滚动
- `history` 命令可以特化渲染成"可点击重新执行"的历史列表,而不是纯文本

### 11. 自动补全与建议

**处理**:
- 输入框支持 Tab 补全(常规终端行为保留)
- 额外提供"自然语言 → 命令"的辅助建议条(可选功能,非必须),例如用户输入"查看当前目录下最大的5个文件",提示可执行 `du -sh * | sort -rh | head -5`,点击即可填入输入框而非直接执行(避免自动执行带来的风险)

## 五、视觉与交互细节规范

- **字体**:输出内容统一用等宽字体(如 JetBrains Mono / Fira Code),避免表格错位
- **配色**:遵循终端配色心智——成功(默认色)/警告(黄)/错误(红)/系统提示(灰),避免过度"聊天软件化"导致失去终端的专业感
- **气泡宽度**:与常规聊天软件不同,终端输出气泡应尽量贴近可用宽度,而不是像聊天消息那样限制窄宽度,否则代码/表格会被挤成多行
- **操作按钮**:每个输出气泡 hover 时显示「复制」「重新执行该指令」「在此指令基础上编辑后执行」三个快捷操作
- **时间戳与耗时**:每条指令气泡显示发出时间,输出气泡显示执行耗时(如 "1.2s"),长任务显示进度或已用时长
- **多会话/多标签**:支持像浏览器标签一样并行开多个终端会话(对应多个 PTY),每个会话是独立的一条聊天流,顶部可切换

## 六、技术实现要点

1. **后端 PTY**:Node.js 用 `node-pty`,Python 用 `ptyprocess`/`pexpect`,起一个真实交互式 shell 进程
2. **通信协议**:WebSocket 全双工,后端把 PTY 的原始字节流通过消息事件推给前端,前端把用户输入(含控制字符如 Ctrl+C = `\x03`)发回后端写入 PTY
3. **ANSI 解析**:引入 `ansi-to-react` / 自研解析器,将转义序列翻译为结构化的富文本片段(颜色、加粗、光标移动指令),而不是把原始转义码显示出来
4. **命令分类器(增强选择器)**:两级判断,输出只用于选择增强视图,不影响真相层的数据流——
   - 静态规则:维护常见命令名单(vim/top/less/htop/ssh 等 → 全屏程序;npm/pip/apt/docker → 可能长任务)
   - 动态特征探测:监测是否出现"备用屏幕缓冲区"转义序列、是否长时间(如 >5s)持续有输出但无终止符、是否输出后无新内容且无换行(疑似等待输入)
5. **终端真相层**:每个会话维护一个常驻的终端仿真状态机(xterm.js 实例,可以是隐藏/无头的),完整消费 PTY 字节流。全屏程序直接呈现该实例;增强气泡切到终端视图时,从真相层重放该命令区间的屏幕状态,避免"检测到全屏前的字节已按文本渲染、无法迁移"的问题
6. **降级原则**:任何增强组件(结构化解析、进度条、输入识别)抛错或不匹配时,一律卸载并回退到终端仿真视图,不允许出现空白或乱码气泡
6. **安全**:密码类输入必须标记为 `sensitive`,在消息持久化/日志中做脱敏存储;危险命令拦截规则应可由用户自定义增删

## 七、边界情况与后续优化方向

- **命令输出格式随环境变化**(比如不同发行版 `ls` 颜色/参数不同):结构化解析器要做好"识别失败自动降级为纯文本"的兜底,不能因为解析出错导致内容丢失或报错崩溃
- **多行输入**(heredoc、粘贴多行脚本):输入框需支持多行编辑与识别,发送时整体作为一条指令气泡
- **窗口尺寸(resize)**:PTY 需要知道终端宽高(尤其影响 vim/top 等全屏程序的渲染),前端要在气泡展开为终端视图时,把当前视图容器尺寸同步给后端 PTY(`ioctl TIOCSWINSZ`)
- **移动端适配**:全屏程序在小屏幕上体验天然较差,可以考虑针对移动端提供"简化只读模式",复杂交互建议引导用户切到桌面端

---

以上方案兼顾了"聊天体验的友好性"与"终端本身不可替代的交互能力(全屏程序、实时流、密码输入)",核心架构原则是:**以真实终端状态为事实来源,分类器只负责选择增强视图;任何分类失败都降级为可用的终端交互**。终端仿真层保证正确性下限,增强层提供体验上限,两层解耦、互不拖累。
